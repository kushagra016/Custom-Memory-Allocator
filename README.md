# Custom Memory Allocator

---

## Project Overview

This project is a C++ based Custom Memory Allocator designed to replace standard operating system memory management. Instead of relying on general-purpose runtime calls like `new` or `malloc()` for every individual memory request, this allocator pre-allocates a massive contiguous chunk of raw memory upfront directly from the OS. It uses a Doubly Linked List paired with hidden `BlockHeader` metadata to manually track, partition, and distribute smaller pieces of this memory arena to the application. This approach effectively bypasses slow OS runtime calls, minimizes overhead, and optimizes memory utilization for custom data structures.

## Problem Statement

General-purpose Operating System memory allocators are inherently designed to handle requests of any size safely, which introduces significant runtime performance overhead. Over time, this generalized approach leads to severe memory fragmentation, creating unusable memory holes (external fragmentation) and wasting space within allocated blocks (internal fragmentation).

## Objectives

- Demonstrate custom allocation from a pre-allocated memory pool.
- Implement First-Fit, Best-Fit, and Worst-Fit block-selection policies.
- Represent the pool as a doubly linked list of block headers.
- Split a free block when it is large enough to hold the requested allocation and a new header.
- Merge a freed block with adjacent free blocks where possible.
- Let the user select the displayed size unit: bytes (B), kilobytes (KB), megabytes (MB), or gigabytes (GB).
- Display active block IDs and a block-by-block memory map.
- Compare the memory layouts generated by all three allocation strategies.
- Summarize used memory, free memory, total pool size, and block count.

## Key Concepts

### Memory pool

The program reserves a contiguous region of memory when each `MemoryAllocator` object is constructed. 

### Block header

Each memory block begins with a `BlockHeader` structure:

```cpp
struct BlockHeader
{
    size_t size;
    bool isFree;
    BlockHeader *next;
    BlockHeader *prev;
};
```

- `size`: size of the block's payload in bytes, excluding its header.
- `isFree`: indicates whether the block is available for allocation.
- `next`: points to the next block in the linked list.
- `prev`: points to the previous block in the linked list.

The pointer returned to the caller points immediately after the block header, so the header is kept separate from the payload.

### Splitting

If the selected free block is large enough to hold the request plus another `BlockHeader` and at least one byte of remaining payload, the allocator splits it into an allocated block and a new free block. If there is not enough room for a new header and payload, the allocator uses the selected block as a whole.

### Coalescing

When a block is deallocated, the allocator marks it free and attempts to merge it with a free next block and then a free previous block. This coalescing can reduce external fragmentation by combining neighbouring free regions.

### Fragmentation

Fragmentation occurs when available memory is divided into pieces that are not equally useful for future requests. A request may fail even when the total free memory is large enough if no individual free block can satisfy the request. The program reports allocation failure when one or more of its three allocator instances cannot satisfy a request.

## Allocation Strategies

### 1. First-Fit

First-Fit traverses the block list from the beginning and chooses the **first free block whose payload size is at least the requested size**.

**Advantages**
- Simple to implement.
- Stops searching as soon as a suitable block is found.

**Trade-offs**
- The chosen block depends on the order of blocks in the list.
- Repeated allocations can leave small free blocks in portions of the pool.

### 2. Best-Fit

Best-Fit scans the list and chooses the **smallest free block that can satisfy the request**.

**Advantages**
- Attempts to leave the smallest remainder among the blocks that can satisfy a request.

**Trade-offs**
- It scans the full block list to identify the smallest suitable block.
- It can create small leftover blocks that may be difficult to reuse.

### 3. Worst-Fit

Worst-Fit scans the list and chooses the **largest free block that can satisfy the request**.

**Advantages**
- Uses the largest available region for the current request.
- May leave a sizeable remainder in that selected region.

**Trade-offs**
- It scans the full block list.
- Its results depend on the sequence and sizes of allocation requests; it is not guaranteed to reduce fragmentation.

No strategy is universally best. Their outcomes depend on the allocation workload and the resulting memory layout.

## Major Features and Modules

### 1. Memory-pool initialization

Each allocator reserves its own memory region using `::operator new(totalSize)`. The initial region is represented by one free block whose payload size is the pool size minus the first header.

### 2. Allocation engine

`MemoryAllocator::allocate()` searches for a suitable free block according to the selected `AllocationStrategy`. It returns `nullptr` when no suitable block is found and otherwise returns a pointer to the block's payload.

### 3. Deallocation engine

`MemoryAllocator::deallocate()` marks the corresponding block as free and attempts to coalesce adjacent free blocks. The menu uses the selected primary strategy to identify which allocation the user wants to release, then releases the matching allocation in all three allocator instances.

### 4. Allocation record tracking

The `AllocationRecord` structure stores the three pointers associated with one successful, synchronized request and the original requested value:

```cpp
struct AllocationRecord {
    void* firstFitPtr;
    void* bestFitPtr;
    void* worstFitPtr;
    double requestedValue;
};
```

This allows the program to keep the three simulations in step: a request is retained only if all three allocators succeed. If any allocator fails, any successful allocations from that request are released and the request is reported as failed.

### 5. Unit conversion

The helper functions `convertToBytes()` and `convertFromBytes()` convert values between bytes and KB, MB, and GB. The program accepts `B`, `KB`, `MB`, and `GB` as the display/input unit. Unit conversion uses powers of 1024.

### 6. Active block IDs

`printActiveBlockIds()` lists block IDs that are currently allocated in the selected allocator. IDs are generated from the current linked-list order, starting at 1.

### 7. Memory-map display

`printMemoryMap()` displays each block's ID, state (`FREE` or `USED`), and payload size in the chosen unit. It also totals the free and used payload bytes represented by the blocks.

### 8. Summary table

`printSummaryTable()` reports the configured pool size, total used payload, total free payload, and number of blocks for the selected allocator.

### 9. Strategy comparison

The comparison menu option prints memory maps for First-Fit, Best-Fit, and Worst-Fit one after another, making their layouts easier to inspect.

## Project Setup / Installation Instructions
1. **Clone the repository:**
   ```bash
   git clone https://github.com/kushagra016/Custom-Memory-Allocator
   cd Custom-Memory-Allocator
   ```
2. **Compile the C++ code:** Ensure you have a modern C++11 compatible compiler (e.g., `g++`) installed on your system.
   ```bash
   g++ main.cpp -o allocator
   ```
3. **Run the executable:**
   ```bash
   ./allocator
   ```
4. **Usage Instructions:** Upon startup, you will be prompted to select your preferred operating unit (B, KB, MB, GB) and a primary Allocation Strategy. You can then navigate the interactive CLI menu to dynamically allocate memory, deallocate using active Block IDs, view the live ASCII memory map, compare all strategies simultaneously, and generate unified summary tables.

## How to Use the Program

### Select a unit

At startup, enter one of:

- `B` — bytes
- `KB` — kibibytes (1024 bytes)
- `MB` — mebibytes (1024² bytes)
- `GB` — gibibytes (1024³ bytes)

The code converts input sizes to bytes internally. Unit names are converted to uppercase. Unrecognized units fall back to `B`.

### Select the primary strategy

Enter a strategy number:

| Choice | Strategy |
|---:|---|
| 1 | First-Fit |
| 2 | Best-Fit |
| 3 | Worst-Fit |

This selection determines which allocator is used for the main map, active block IDs, deallocation ID lookup, and final summary. Allocation requests are still attempted in all three allocators.

### Main menu

| Option | Action |
|---:|---|
| 1 | Allocate memory in all three allocators. |
| 2 | Deallocate a selected active block across all three allocators. |
| 3 | Display the primary allocator's memory map. |
| 4 | Display memory maps for all three strategies. |
| 5 | Exit and show the primary allocator's summary. |

### Allocate memory

Choose option `1` and enter the amount in the unit selected at startup. If all three allocators can satisfy the request, the allocation is recorded. If any one fails, the program rolls back successful allocations for that request and reports failure.

### Deallocate memory

Choose option `2`. The program displays active block IDs from the primary allocator. Enter an active ID. If that block corresponds to a tracked allocation, the program releases the matching pointers from all three allocators.

**Note:** Block IDs are based on the current block-list order and can change when blocks are split or merged. Use the active IDs displayed immediately before entering the ID.

### Display and compare

- Choose option `3` to see the primary allocator's current block layout.
- Choose option `4` to print all three layouts and compare how the policies have placed the allocations.

### Exit

Choose option `5` to display the summary table for the primary allocator and terminate the program.
